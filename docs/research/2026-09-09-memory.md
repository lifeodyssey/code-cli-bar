# Background usage scan memory investigation

## Observed failure

Code CLI Bar 1.6.0 (52), macOS 26.5.2, after approximately 53 hours:

- RSS at the first sample: 1,555,936 KiB (1.48 GiB).
- `vmmap` physical footprint: 1.4 GiB; lifetime peak: 4.8 GiB.
- Live malloc allocations: 26.3 MiB, versus 1.2 GiB of dirty/swapped
  allocator fragmentation. The process was idle in a three-second stack
  sample. This evidence points to allocation peaks and retained pages;
  it does not establish an unbounded live-object leak. A later refresh-time
  stack sample confirmed execution in the production cost-scanning and
  fingerprint-cache paths.
- The configured usage refresh interval was 60 seconds.
- The Claude cache was 71.7 MiB, with 135,444 events from 5,056 files.
  The 64 MiB reader guard rejected it on every pass even though the writer
  successfully saved it. This forced repeated parsing of a 2.3 GiB tree.
- Codex logs occupied 12.8 GiB; the largest individual file was 3.5 GiB.

Only file sizes, counts, process metrics, and sanitized stacks were used in
the report. Original session stores and credentials were not modified.

## Change

The cost scanner now drains temporary Foundation objects after each read
and parsed record. The reader retains its scan cursor across chunks, so a
long record is not repeatedly rescanned. Compressed DSH streams share that
reader, and OpenCode JSON parsing drains temporary objects after each row.
Session-kit transcript APIs and the dependency pin are unchanged.

The scan-cache guard is 256 MiB and reads use mapped input. This admits the
observed valid cache without an extra encoded-data copy. It remains a finite
guard: installations exceeding 256 MiB per provider can still require full
rescans; a sharded cache would be a separate storage change. Usage counts,
deduplication, retention, and privacy-safe cache fields are unchanged.

Local autorelease pools are the technique Apple documents for temporary
growth in large Foundation loops, including Swift:
[Analyze heap memory, WWDC24](https://developer.apple.com/videos/play/wwdc2024/10173/)
and [Using Autorelease Pool Blocks](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/MemoryMgmt/Articles/mmAutoreleasePools.html).

## Controlled comparison

Both optimized standalone executables read the same synthetic 134.08 MiB
JSONL file and parse the same nested JSON records. The baseline compiles
the pinned kit's original reader; the changed version compiles the exact
`CostUsageLineReader.swift` used by the application. An outer pool gives
both runs the same lifetime boundary. `/usr/bin/time -l` measures the whole
process. Other local compilation was active, so elapsed time is not used
as a performance claim.

| Measurement | Original | Changed |
| --- | ---: | ---: |
| Records delivered | 24,000 | 24,000 |
| Sum of synthetic counters | 118,080,000 | 118,080,000 |
| Peak physical footprint | 223,445,592 bytes | 2,261,400 bytes |
| Maximum RSS | 83,771,392 bytes | 6,733,824 bytes |

The synthetic peak footprint fell by 99.0%. This is a parser benchmark,
not a claim that the complete application's memory falls by the same ratio.

## Validation

Production-entry-point tests cover empty files, read failures, blank lines,
UTF-8/CRLF records, chunk boundaries, long records, and an unterminated tail.
Cache tests cover reuse beyond 64 MiB, unchanged token values, fingerprint
invalidation, and rejection above the remaining guard. Existing cost,
privacy, compressed-history, and ledger tests exercise the calling pipeline.

The complete suite passed 1,771 tests with zero failures; one opt-in live
pricing-network test was skipped by its existing environment gate. Debug
build and release packaging passed with the Xcode toolchain. Strict deep
signature verification passed, the entitlements were empty, and both the
packaged and build-output binaries had the same UUID. Version 1.6.1 (53)
replaced the existing local 1.6.0 process at its original bundle path.

The 15-minute monitor completed all 900 seconds with 177 samples. RSS
median was 157.3 MiB, range 23.7–967.19 MiB, and final RSS was 88.58 MiB.
Minute-level physical-footprint samples repeatedly returned to 40–110 MiB
between refresh peaks; the recorded peak reached 972.2 MiB. A further
check after 97 minutes found the same process alive, physical footprint
94.6 MiB and lifetime peak 1.1 GiB. Enabled providers' cost snapshots
continued updating. This shows recovery between real refreshes, rather
than the old persistent gigabyte footprint; transient refresh peaks remain.
The 97-minute run is shorter than the original 53-hour baseline, so the
scheduled 24-hour observation remains a separate follow-up.

Native UI selection timed out, so the local smoke check verified process,
bundle, signature, and live snapshot output; it did not verify interactive
popover behavior. No UI code changed in this patch. CI and downloaded
release-asset verification are recorded in the release PR.

`Scripts/monitor_memory.py`
records RSS every five seconds and physical footprint once a minute, stops
if the process identity changes, and writes a CSV plus a completion summary.
